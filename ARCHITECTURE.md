# Phylo-BGC architecture

## The core relationship

```
Taxon → Genome → Phylogenetic Node → BGC → BGC Family → Product/Compound
```

Per the original product report (§14), this relationship — not the tree
visualization — is Phylo-BGC's core intellectual and engineering asset. If
it's designed correctly, new predictors, taxonomic frameworks, and chemical
resources can be plugged in later without rebuilding the platform. Everything
below is in service of getting this relationship right early.

## Separation of concerns

- **`engine/`** — a standalone, installable Python package (`bgcscape`).
  Owns the data model, and will own ingestion and analysis logic as those
  are built. It has zero dependency on any web framework and must remain
  usable from a CLI, a Jupyter notebook, a test suite, or a future API layer
  without modification.
- **`web/`** (not yet built) — will consume the engine (directly as a
  library from a Python API layer, or by shelling out to the CLI) rather
  than re-implementing any biological logic in TypeScript.

This is a deliberate constraint, not a default. The temptation in a project
like this is to let query logic leak into API route handlers or React data
hooks; the rule is that anything with scientific meaning (what counts as a
"novel" BGC, how a family is defined, what evidence-level a computed fact
gets) lives in `engine/`, is unit-tested there, and the web layer only
requests and renders it.

## Provenance is structural, not conventional

Every scientific row in the core model — `Taxon`, `Genome`,
`PhylogeneticTree`, `BGC`, `BGCFamily`, `Compound`, `BGCCompoundLink` —
inherits `ProvenanceMixin`, which makes `source_id` (FK → `Source`) and
`evidence_level` **non-nullable**. It is a schema-level constraint error, not
a code-review nit, to insert a fact into Phylo-BGC without saying where it
came from and how confident the platform is in it.

`EvidenceLevel` (`engine/src/bgcscape/models/base.py`) has four values:

| Level | Meaning | Example |
|---|---|---|
| `OBSERVED_CURATED` | Directly reported by a canonical reference/publication | A MIBiG experimentally-characterized BGC→compound link |
| `COMPUTED` | Deterministic output of a versioned pipeline over other stored data | A BiG-SCAPE family assignment, an IQ-TREE placement |
| `PREDICTED` | Output of a heuristic/probabilistic tool with real uncertainty | An antiSMASH BGC boundary/class call |
| `HYPOTHESIZED` | A hypothesis generated by Phylo-BGC or a user, not a tool output | A future "this looks novel" flag |

This is the mechanical enforcement of the "never claim proof of novelty,
never fabricate data" principle: the UI (once built) can style/label facts
by evidence level, and it is structurally impossible to add a row that
skips this decision.

## Why `native_enum=False` everywhere

All SQLAlchemy `Enum` columns (`TaxonRank`, `BGCClass`, `EvidenceLevel`,
`SourceType`, `AssemblyLevel`) are declared with `native_enum=False`, which
stores them as `VARCHAR` + `CHECK` constraint instead of a Postgres native
`ENUM` type. The tradeoff is deliberate: native Postgres enums require
`ALTER TYPE ... ADD VALUE` (with real transactional gotchas) every time a
new BGC class or taxonomic rank shows up, and Phylo-BGC's whole premise is
that the underlying annotation vocabularies (antiSMASH rule categories in
particular) will keep evolving. A `VARCHAR` + `CHECK` migrates like any
other column change.

## Dual-dialect types: Postgres in production, SQLite in tests

Production targets PostgreSQL (per the report's tech stack). The automated
test suite runs against **in-memory SQLite** for speed and zero setup —
appropriate for unit-testing ORM relationships, constraints, and business
logic, but not a substitute for testing against real Postgres before
shipping a schema change. Two mechanisms make this safe:

1. **`sqlalchemy.Uuid`** for all primary/foreign keys — a dialect-agnostic
   type that uses Postgres's native `UUID` in production and falls back to
   `CHAR(32)` on SQLite, with no code difference.
2. **`JSONVariant`** (`engine/src/bgcscape/models/types.py`) — generic JSON
   that becomes Postgres `JSONB` specifically in production
   (`JSON().with_variant(JSONB(), "postgresql")`), used for `BGC.raw_annotation`
   and `Genome.sample_metadata`.

`docker-compose.yml` and the CI workflow (`.github/workflows/ci.yml`) run
the same test suite against a real Postgres service container — the CI file
is a strong first draft but, honestly, **unvalidated by an actual GitHub
Actions run** as of this chunk (the build sandbox has no CI access). Treat
the SQLite results in `PROGRESS.md` as "the logic is correct"; treat a real
CI run as the remaining step before calling the schema production-ready.

## Known, deliberate simplifications (not oversights)

- **`BGC.bgc_class` is single-valued.** antiSMASH regions can be
  multi-class/hybrid; for MVP this is captured via the `HYBRID` enum value
  + free-text `subtype` + the full predictor output preserved in
  `raw_annotation` (JSON), rather than a `BGC ↔ BGCClass` many-to-many
  table. Nothing is lost — `raw_annotation` retains full fidelity — but a
  future migration to many-to-many is plausible once real antiSMASH exports
  are being ingested and the single-class simplification starts to hurt.
- **`PhylogeneticTree` stores either an inline Newick string or an
  object-storage URI (or both), enforced by a `CHECK` constraint.** Small
  example/reference trees can live inline; real trees (tens of thousands of
  tips) should go to S3-compatible storage per the report's architecture
  (§ Backend & Storage), with only the URI in Postgres.
- **No novelty-scoring table yet.** The report's §8 "novelty score" is a
  Phase 5 feature. Building it now, before any real BGC corpus exists to
  validate a scoring formula against, would be exactly the kind of
  premature complexity the "avoid overengineering" principle warns against.

## What Phase 1a deliberately does not include

Ingestion code (MIBiG/GTDB/antiSMASH import), any HTTP/API layer, the
frontend, BiG-SCAPE/CORASON orchestration, novelty scoring, user uploads.
See `PROGRESS.md` for the phase tracker and what's next.

## Phase 1b: ingestion architecture

Every source module (`engine/src/bgcscape/ingest/{mibig,gtdb}.py`) follows
the same two-stage shape, deliberately kept separate:

- **`parse_*()`** — pure function, raw external format → a plain
  dataclass. No database access, so it's unit-testable without a session
  or fixtures.
- **`load_*()`** — dataclass + `Session` + the source's `Source` row →
  idempotent upsert of ORM objects. Safe to re-run over a refreshed
  export.
- **`ingest_*()`** — orchestrates a batch: loops records, applies any
  source-specific filtering (e.g. MIBiG's retired-entry skip), and never
  lets one bad record abort the run.

Schemas parsed against MIBiG/GTDB's *real* formats, not assumptions —
verified by cloning `mibig-secmet/python-mibig` and
`Ecogenomics/GTDBTk`/an nf-core pipeline doc from GitHub (in this
sandbox's network allow-list) rather than trusting training-data memory of
older MIBiG/GTDB versions. See `docs/DATA_SOURCES.md`.

### Idempotency: `get_or_create_or_update`

Ingestion has to be safe to re-run without duplicating rows, and *should*
refresh stale fields when re-run against newer source data — a different
default than a typical web app's "create once" flow. `ingest/_util.py`'s
`get_or_create_or_update()` is the one place this logic lives, used by
every loader. Two non-obvious behaviors, both added after being caught by
this project's own tests (see "Real bugs found" below), not designed in
up front:

1. A `None` in the update payload never overwrites an existing non-None
   value — a source that simply doesn't carry a field shouldn't be able to
   erase a fact a *different* source already recorded for the same row.
2. `fallback_lookups`: when two sources' natural keys can identify the
   same real-world entity (MIBiG's `Taxon` lookup is `ncbi_taxid`; GTDB's
   is `(rank, name)`), a bare single-key lookup only merges correctly in
   one ingestion order. `fallback_lookups` tries secondary keys before
   giving up and creating a new row, and once a fallback match is found,
   backfills the primary key's fields onto it — making the merge order-
   independent. This is a deliberately narrow fix for a specific observed
   collision, not a general multi-source entity-resolution system.

**Known limitation, left as-is for this chunk:** when two sources' rows
merge, `source_id`/`evidence_level` end up reflecting whichever source
touched the row *last*, not "all sources that ever asserted something
about it." Real per-field provenance (a fact-level, not row-level,
attribution model) would need a bigger schema change — a legitimate future
direction, not attempted here.

### MIBiG loci are not genomes

A MIBiG entry's `loci[].accession` is a single deposited GenBank locus
(often just the BGC region itself), not a `GCA_`/`GCF_` whole-assembly
accession. Modeling it as a full `Genome` row would be a category error —
assembly-level QC fields (completeness/contamination) don't apply to a
locus deposit. This is why `AssemblyLevel.LOCUS` exists: a genuine,
additive vocabulary extension that `native_enum=False` was specifically
chosen to make painless (see above) — first real validation of that Phase
1a design bet paying off.

### Transaction strategy: one commit per record, not per batch

`ingest_mibig_entries()`/`ingest_gtdb_metadata()` commit after each
successfully-loaded record, not once at the end of the whole batch. A
single all-encompassing transaction would mean one bad record's rollback
silently discards every good record processed earlier in the same run —
caught by this project's own `test_ingest_records_parse_errors_without_aborting_batch`
test failing against the first (batch-transaction) implementation.

### Real bugs found and fixed in this chunk (via actual execution, not review)

Listed explicitly because they're the kind of thing worth knowing about
before extending this code further:

1. **`SAEnum(..., native_enum=False)` was not actually creating a CHECK
   constraint.** `create_constraint` defaults to `None`
   (effectively off) in SQLAlchemy 2.0 for non-native enums — Phase 1a's
   `ARCHITECTURE.md` claimed "VARCHAR + CHECK constraint" but only
   `validate_strings=True`'s *Python-side* check was actually running.
   Anything writing to the database outside this ORM had zero protection
   against an invalid enum string. Fixed by passing `create_constraint=True`
   explicitly on all five enum columns, confirmed by inserting an invalid
   value via raw SQL (bypassing the ORM entirely) and watching SQLite
   reject it.
2. **Enum columns were storing the Python member *name*
   (`"OBSERVED_CURATED"`), not the `.value` the enums were deliberately
   defined with (`"observed_curated"`).** SQLAlchemy's default for a
   `(str, Enum)` hybrid is name-based storage; every enum was explicitly
   given lowercase snake_case values for a reason (matching what Pydantic
   already emits in JSON), so this was a silent contract violation between
   the raw database and every API/schema response. Fixed with
   `values_callable=lambda enum_cls: [m.value for m in enum_cls]` on all
   five enum columns.
3. **The cross-source Taxon merge bug** described above under
   `get_or_create_or_update`.
4. **A batch-transaction bug** in the ingestion orchestrators, described
   above under "Transaction strategy."
5. Alembic's `--autogenerate` reliably emits
   `postgresql.JSONB(astext_type=Text())` without importing bare `Text` —
   confirmed to recur on a second, independent autogenerate run in this
   chunk (not a one-off from Phase 1a). Documented directly in
   `models/types.py` where `JSONVariant` is defined, since that's where
   someone regenerating a migration would need the reminder.

None of these were caught by writing the code carefully — all five were
caught by actually running it (executing raw SQL against the resulting
database, running the CLI against fixture data in more than one order,
promoting SQLAlchemy warnings to hard errors in the test suite) in this
sandbox. That's the practical case for the "verified in this sandbox, not
just written" framing PROGRESS.md uses.

### What Phase 1b deliberately does not include

antiSMASH region-JSON ingestion (MVP v2 in the original product report,
not MVP v1 — MIBiG + GTDB was the deliberate scope for this chunk),
BiG-SCAPE family-clustering ingestion, any HTTP/API layer, the frontend,
novelty scoring, user uploads, full multi-source per-field provenance.

## Phase 2 (in progress): visualization API + design prototype

### API layer: `bgcscape.api`, read-only, UI-shaped

`engine/src/bgcscape/api/` is a FastAPI app, gated behind an `api` extra
(`pip install -e ".[api]"`) so the core engine/ingest/CLI stay free of a
web-framework dependency, per the separation-of-concerns principle. Its
schemas (`api/schemas.py`) are deliberately **not** the same as
`bgcscape.schemas` (the engine's general Create/Read contracts used by
ingestion) — `TaxonTreeNode.genome_count` and `.bgc_class_counts` are
aggregated across every descendant, which has no equivalent column
anywhere in the database. This is UI-shaped response data, built for one
consumer (the tree visualization), not a general CRUD API.

`api/tree_builder.py` loads the whole taxonomy + genome + BGC set into
memory and aggregates counts via Python post-order recursion, rather than
a recursive SQL CTE — correct and simple at fixture/demo scale, a
deliberate simplification to revisit with a CTE or materialized-path
approach once real dataset size makes an in-memory build impractical.

**Taxonomy vs. phylogeny, said explicitly because it's easy to blur:**
what this renders is the GTDB *taxonomic* hierarchy (`Taxon.parent_id`),
not an inferred *phylogeny* with branch lengths. The data model has a
separate `PhylogeneticTree`/`PhylogeneticNode` pair (Phase 1a) for that,
but nothing populates it yet — MAFFT/IQ-TREE orchestration is still-future
work. Taxonomy and phylogeny are highly correlated but not identical;
presenting one as the other without saying so would cut against this
project's own epistemic-rigor principle. The UI should say "taxonomic
tree," not "phylogeny," until real tree inference exists.

### Design prototype before production frontend code

`web/design-prototype/tree-explorer-demo.jsx` is a single-file React/D3
prototype (a Claude.ai artifact) built to get real, immediately-
interactive feedback on the visual/interaction direction before writing
the production Next.js implementation — see its own README for what was
actually verified (real Babel transpilation, real `react-dom/server`
rendering, a targeted unit-test suite for the pure filtering/tree logic)
versus what wasn't (actual visual appearance, real click simulation).

Visual direction follows the original brief's explicit instruction
("calm, precise scientific instrument... Nature/Cell data graphics, not a
flashy SaaS dashboard") rather than a generic default: quiet cool-neutral
background (not the common warm-cream AI default), IBM Plex Sans/Mono
(technical-instrument feel), italic taxonomic names (a genuine scientific
convention), and a signature element — small colored tick marks per BGC on
each genome tip, like a genomic ideogram/barcode — grounded in real genome-
browser vernacular and directly serving the brief's "scan for biosynthetic
hotspots" use case, not decorative color.

### Real bugs found this sub-chunk

1. **SQLite `:memory:` is per-connection by default.** The first API test
   fixture seeded data on one connection and queried it via the FastAPI
   dependency's own session (a different pooled connection) — which saw an
   empty database ("no such table"). Fixed with `poolclass=StaticPool` to
   share a single connection across the whole test.
2. **Hybrid-BGC filtering bug in the design prototype**: the class-count
   panel correctly decomposed a hybrid (e.g. NRPS+PKS) BGC into its
   component classes, but the tree's dimming logic checked the literal
   string `"hybrid"` against the active-filter set, which can never match
   (`"hybrid"` isn't a real filter option). A genome whose only NRPS
   activity came from a hybrid BGC would have been wrongly dimmed when
   filtering to "NRPS only." Fixed with a shared decomposition helper used
   consistently by both the count panel and the dimming check; locked in
   with a targeted logic test. Full detail in the prototype's own README.

### What Phase 2 still needs (explicitly not done yet)

The **production Next.js/TypeScript frontend** itself — the prototype
validates direction, it isn't the deliverable. Also not done: wiring the
frontend to a real, running API (`uvicorn` was only run manually in this
sandbox to smoke-test endpoints, not as a persistent service); search/
filter UI in the *production* app (present in the prototype, not yet
ported); publication-grade SVG/PDF export (report §1 "Publication-First");
Web Worker offloading for large trees (tech stack calls for this at scale;
premature at fixture-size data).

## Phase 2 (complete): production Next.js frontend

### Generated, not hand-maintained, type boundary

`web/src/lib/api-schema.generated.ts` is generated directly from the
FastAPI app's own OpenAPI schema via `openapi-typescript`
(`bgcscape dump-openapi-schema` → `npm run generate-api-types`), not
hand-written to mirror `bgcscape.schemas`/`bgcscape.api.schemas`. This is
a direct response to this project's own track record: two separate real
bugs this build already found (enum storage using `.name` instead of
`.value`; a schema-shape assumption that turned out wrong for GTDB
metadata columns) both came from *believing* a shape matched reality
without checking. A hand-maintained parallel type definition is exactly
the kind of thing that would drift silently; a generated one can't.

### Architecture improvement over the prototype, found while porting

The prototype (`web/design-prototype/`) pre-pruned the tree into a new
collapse-aware copy before handing it to `d3.hierarchy()`. The production
version (`web/src/lib/tree-logic.ts`) instead passes a **children-accessor
function** to `d3.hierarchy(root, accessor)` that itself checks collapse
state — `d3.hierarchy` is built for exactly this, and it avoids re-deriving
a parallel "pruned tree" data shape on every collapse toggle. Ported code
should be re-examined for this kind of thing, not copied mechanically —
the hybrid-filtering bug pattern (getting a decomposition right in one
place but not a structurally-similar other place) was worth designing
around directly rather than just fixing the two call sites again.

### Self-hosted fonts: a second real network-boundary finding

`next/font/google` fetches font files from `fonts.googleapis.com` **at
build time** (that's how it self-hosts for production — download once,
serve locally, no runtime request to Google). This sandbox's network
allow-list doesn't cover that domain, so the first `next build` attempt
failed outright — the same *class* of constraint as MIBiG/GTDB not being
reachable from `bash_tool` in earlier chunks, encountered again in a
different subsystem. Fixed by fetching the real IBM Plex Sans/Mono
`.woff2` files from IBM's own open-source repository (github.com/IBM/plex,
SIL Open Font License) and switching to `next/font/local` — functionally
the same end state `next/font/google` would have produced, verified to
actually build rather than assumed. See `web/README.md` for detail and how
to switch back if building somewhere with normal internet access.

### What was actually verified, in order

Every step below was run for real in this sandbox, not assumed from
writing the code carefully:

1. `npm install` — 0 vulnerabilities after upgrading Next.js 14→16 (14.x
   had no further stable patches available) and force-upgrading Vitest to
   resolve a dev-only esbuild advisory.
2. `npx tsc --noEmit` — clean after fixing one real type mismatch (a
   Pydantic `Optional[str] = None` field generates as `string | null |
   undefined` in the OpenAPI schema, not `string | null` — the function
   signature was widened to match the real generated type, not
   patched around at call sites).
3. `npx vitest run` — 24 tests, including a direct regression test for
   the hybrid-BGC filtering bug (ported from the prototype's manual
   verification into an actual automated test) and new tests for the D3
   layout logic (leaf-count-driven height, collapse removing descendants
   from `d3.hierarchy()` output, finite coordinates on every node).
4. `next build` (production, Turbopack) — succeeded after the font fix.
5. **Full end-to-end**: real `uvicorn` process + real `next start`
   production server, both running simultaneously, hit with real `curl`
   requests — confirmed the served HTML contains expected content (header,
   search box, the correct client-side-fetch loading state), confirmed
   self-hosted font preload links resolve to real hashed filenames, and
   confirmed the API's CORS configuration actually permits the frontend's
   origin (`access-control-allow-origin: *`) rather than assuming the
   `CORSMiddleware` config from Phase 2's API work was sufficient.

One thing not verified, stated plainly rather than glossed over: **actual
visual rendering**. This sandbox has no browser. Everything above confirms
the app builds, serves, and is logically correct — not that it looks
right. Open `npm run dev` yourself before treating the visual output as
settled.

## Phase 1c: antiSMASH + BiG-SCAPE ingestion

Completes the backend data layer: predicted BGCs at genome scale
(antiSMASH) and their family groupings (BiG-SCAPE), alongside the curated
MIBiG/GTDB reference layer from Phase 1b. Both parsers were written
against the tools' **real, source-verified** output formats — cloned from
`antismash/antismash` and `medema-group/BiG-SCAPE` on GitHub — not from
recalled or assumed schemas. See `docs/DATA_SOURCES.md` for the full
field-level verification trail.

### The cross-tool join key is real, not invented

antiSMASH names each region's GenBank file
`f"{record.id}.region{number:03d}.gbk"`. BiG-SCAPE's clustering output
identifies each record by exactly that filename stem in its `GBK` column.
So the two tools already share a join key; Phylo-BGC just has to store it.
That's what `BGC.external_ref` (new this phase) is: antiSMASH ingestion
writes the stem, BiG-SCAPE ingestion matches on it directly. No
transformation, no Phylo-BGC-specific convention, nothing to keep in sync
between two independently-written parsers — `region_external_ref()` in
`ingest/antismash.py` is the single definition both sides reference.

### antiSMASH's JSON cannot tell you which genome it ran on

There is no assembly-accession field anywhere in antiSMASH's output — it's
organized around "one run over some input sequences," not "one assembly."
Rather than guess (e.g. by scraping `input_file`, which is just whatever
path the user happened to pass), `--genome-accession` is a **required**
argument on both the library function and the CLI. Guessing here would
manufacture a provenance claim that the source data doesn't actually
support, which is the specific failure mode this project's epistemic-rigor
principle exists to prevent.

The corresponding `Genome` stub antiSMASH ingestion creates uses the new
`AssemblyLevel.UNKNOWN` — an explicit "not known" rather than a plausible
default like `CONTIG`. And when the genome already exists (e.g. from GTDB),
the loader passes `update_existing=False` so antiSMASH's placeholder values
can never overwrite real assembly metadata another source already
established.

### Family labels are cutoff-scoped

`FAM_00001` at cutoff 0.3 and `FAM_00001` at cutoff 0.7 are *different
groupings that happen to share a label* — BiG-SCAPE renumbers per run.
Families are therefore keyed on `(source_id, label, clustering_cutoff)`,
never label alone. Ingesting the same file at two cutoffs correctly
produces two distinct families (there's a test for exactly this).

### Unmatched rows are expected, not errors

Real BiG-SCAPE runs routinely include MIBiG reference BGCs for comparison.

**Superseded (MIBiG 4.0 chunk):** those rows used to be unmatchable, because
MIBiG ingestion had no antiSMASH region filename to derive an `external_ref`
from, and `IngestReport` counted them as `skipped`. That threw away the most
useful thing such a run reports — *which characterized cluster your novel one
groups with*. MIBiG distributes one GenBank per entry named
`<accession>.gbk`, and BiG-SCAPE keys its output on exactly that filename
stem, so MIBiG ingestion now sets `external_ref` to the entry accession and
those rows join like any other. A BiG-SCAPE run over MIBiG's own GenBank
files therefore needs no mapping step at all.

Rows that still don't match are genuinely unknown records, and remain
`skipped` with the CLI's explanatory note — so an operator seeing
"skipped=1" still knows whether that's benign or a sign antiSMASH ingestion
hasn't run yet.

### Real bugs found this phase (all by running the code, not reading it)

1. **The most consequential one: mapping BGC class from the wrong field.**
   The first implementation read `area["products"]`, which sounds like the
   product category but actually holds antiSMASH's fine-grained *rule
   names* ("T1PKS", "NRPS-like", …). The real 7-value category vocabulary
   lives on each protocluster's `category`. Caught by a test asserting a
   hybrid region's subtype was `"NRPS+PKS"` and getting `"NRPS+T1PKS"` —
   which would have silently misclassified a large fraction of real
   antiSMASH regions as `OTHER`, since rule names don't match category
   names.
2. **An Alembic migration that would have silently destroyed every CHECK
   constraint.** `--autogenerate` detected all named CHECK constraints
   across every table as "removed" and emitted drops for all of them in
   `upgrade()` — recreating none. Applying it as generated would have
   undone the Phase 1b constraint fix entirely. Two-part fix:
   `render_as_batch=True` for SQLite in `migrations/env.py` (SQLite has no
   real `ALTER TABLE DROP CONSTRAINT`, so Alembic must use its
   recreate-table strategy), and **hand-writing** the migration to touch
   only what actually changed. **Takeaway for future schema changes in
   this project: never apply an autogenerated migration involving CHECK
   constraints without reading it first.** Alembic's CHECK diffing is not
   reliable here.
3. **A fixture-directory collision that was also a real code fragility.**
   Adding an antiSMASH fixture to the shared test-fixture directory broke
   MIBiG's directory-glob ingestion, which globbed `*.json` and fed
   foreign JSON straight into the MIBiG parser. Fixed on both sides:
   fixtures reorganized into per-source subdirectories, *and*
   `read_mibig_entries_from_path()` now skips files lacking MIBiG's
   mandatory top-level keys with a warning. The second half matters
   beyond tests — a real user pointing at a mixed directory previously got
   confusing "missing required field: 'accession'" errors instead of a
   clear signal.

### Verified end-to-end

The full four-source pipeline was run through the actual CLI against a
real SQLite database: GTDB → MIBiG → antiSMASH → BiG-SCAPE. Confirmed by
querying the resulting database directly that antiSMASH's BGCs attached to
GTDB's *existing* genome row (preserving `complete_genome` and
`completeness_pct=99.87` rather than overwriting them with placeholder
values), and that BiG-SCAPE's families joined to the right BGCs via
`external_ref`. Then confirmed the API surfaces the result — the taxonomy
tree endpoint now returns `{'nrps': 2, 'hybrid': 2, 'terpene': 1}`,
mixing curated MIBiG and predicted antiSMASH BGCs on the same tree.

## Postgres verification (finally done)

For four chunks, every database check in this project ran against SQLite,
with Postgres listed in PROGRESS.md as "the single biggest untested
assumption." It turned out to be installable in the build sandbox from the
Ubuntu archive, so it got tested properly against **PostgreSQL 16.15**:

- Both Alembic migrations apply cleanly (`Context impl PostgresqlImpl`,
  transactional DDL — a genuinely different code path from SQLite's
  batch/recreate strategy).
- The schema is really Postgres-native, not a lowest-common-denominator
  fallback: `id` columns are true `uuid` type, `raw_annotation` and
  `sample_metadata` are `jsonb` (not plain `json`), and all 12 named CHECK
  constraints exist in `pg_constraint`. The `JSONVariant` and
  `sqlalchemy.Uuid` decisions from Phase 1a did exactly what they claimed.
- The full four-source ingestion pipeline produces byte-identical results
  to SQLite, including the cross-source merge preserving GTDB's
  `completeness_pct=99.87` when antiSMASH later touches the same genome.
- **The entire test suite passes on both dialects.**

### The CI workflow had been silently testing SQLite twice

`.github/workflows/ci.yml` has had a "Run test suite against real
Postgres" step since Chunk 1. It set `BGCSCAPE_DATABASE_URL` — but
`tests/conftest.py` hardcoded `sqlite+pysqlite:///:memory:` and ignored
the environment entirely. That step re-ran the SQLite suite and reported
success: a green check mark verifying nothing, for four chunks.

Fixed by making `conftest.py` honor `BGCSCAPE_TEST_DATABASE_URL`.
Deliberately a *different* variable name from the application's
`BGCSCAPE_DATABASE_URL`, so that pointing the app at a database can never
cause a test run to drop and recreate that database's schema — the test
fixture does `DROP SCHEMA public CASCADE` between tests, which would be
catastrophic if it ever pointed somewhere real.

General lesson worth keeping: a CI step that *can't fail* is worse than no
CI step, because it converts "untested" into "believed tested."

## Phase 3: BGC family features

### API

`GET /api/v1/families` and `GET /api/v1/families/{id}`, plus `family_ids`
threaded onto every `BGCSummary` in the tree response so the frontend can
highlight family membership without a second round-trip per BGC.

`family_ids` is a **list**, not a single value, because the same BGC is
legitimately in different families at different BiG-SCAPE cutoffs (see
`ingest/bigscape.py`). Collapsing it to one id would silently pick an
arbitrary cutoff's answer.

`BGCFamilySummary.taxon_names` is the deliberate design choice here. It
rolls up which organisms a family actually spans, which is what makes the
list answer the original report's core question directly — *is this family
confined to one clade, or scattered across phylogenetically distant
organisms?* A family spanning several taxa is exactly the
horizontal-transfer / convergent-evolution signal the product exists to
surface, so it's visible in the list itself rather than behind a click.

### Frontend

Family selection dims everything in the tree the family doesn't reach, so
its distribution reads at a glance. This **stacks with** class filtering
rather than replacing it — both can be active at once.

Family-member BGC ticks get a **ring**, not a color change: the tick's fill
already encodes BGC class, and that has to stay readable while a family is
selected. Same principle as the hybrid split-marker from Phase 2 — don't
overload a channel that's already carrying information.

The membership predicates (`bgcInFamily`, `genomeHasFamily`,
`nodeHasFamily`) live in `tree-logic.ts` as pure functions, unit-tested,
for the same reason the class-filtering logic does: the hybrid-class bug
in Phase 2 happened precisely because one decision was implemented in two
places that drifted apart.

### A test that had been passing by accident

`test_bgc_detail_includes_compounds` grabbed "the first BGC in the tree"
and asserted it had compounds. That held only while the API fixture was
MIBiG-only. Adding antiSMASH data to the fixture (antiSMASH predicts
cluster boundaries and class but says nothing about products) broke it —
correctly. Now split into two explicit tests: a MIBiG-derived BGC *must*
carry curated compounds, and an antiSMASH-derived one *must* report an
empty list rather than anything invented.

## Phase 3 (cont.): comparative clade analysis

`GET /api/v1/compare?taxon_ids=...&taxon_ids=...` answers the original
report's §4.7 question — "what biosynthetic capabilities distinguish these
groups?" — for two to six clades.

### The rigor problem is the design problem

Comparing clades is where a tool like this most easily produces confident
nonsense, so most of the design effort went there rather than into the
statistics:

- **Every count is paired with a per-genome rate.** Two clades almost
  never have the same number of genomes; raw counts between a 40-genome
  clade and a 3-genome clade mostly measure sampling effort. The UI leads
  with the rate and shows the count in parentheses, because the count is
  what tells a reader whether the rate rests on enough data to mean
  anything.
- **`comparable: false` when sampling is thin or lopsided.** Below 3
  genomes, per-genome rates are dominated by individual genomes; beyond a
  10x size imbalance, raw counts are mostly sampling artifact. The
  response is still returned — the flag governs *presentation*, not
  availability, and the frontend renders a prominent warning above the
  table rather than suppressing the numbers.
- **`only_in_this_clade`, never `absent_from_others`.** This is the
  naming decision that matters most. A family missing from a clade's
  profile means no genome *in this dataset* was found to carry it, which
  conflates true absence with incomplete sampling, assembly gaps, and
  prediction sensitivity. The caveat saying exactly that is returned on
  *every* comparison, including well-sampled ones, and is rendered above
  the table — burying it underneath would mean most readers form
  conclusions before reaching it.
- **No p-values.** Enrichment testing across clades needs a model of
  phylogenetic non-independence (closely related genomes are not
  independent samples). Without one, a naive p-value would be worse than
  no p-value, so the API reports none and says so.

### Deliberate partitioning choice

Families present in *some but not all* clades (when comparing 3+) land in
neither `shared_families` nor any clade's `only_in_this_clade`. "In two of
three" is a genuinely distinct and less interpretable situation than
either universal or unique; folding it into one of those buckets would
misrepresent it. There is a test asserting this specifically.

### A real bug caught by that test

`partition_families()` initially filtered to clades that *have* families
before intersecting them — which meant a clade with no families was
silently excluded from the "shared by every clade" calculation, so a
family could be reported as universal even when one of the compared
clades plainly lacked it. Caught by both the three-clade test and the
empty-clade test. The intersection now runs over every profile: if any
clade lacks a family, that family is not shared, and a clade with nothing
in it means nothing is shared.

### Interaction design

Shift-click a taxon label toggles it into the comparison; plain click
stays collapse/expand. Collapse/expand is by far the more frequent action
and shouldn't get harder to reach because a second mode exists. Selected
clades are marked with a ◆ and the signal color, and the header carries a
"shift-click a clade to compare" hint, since a modifier-key interaction is
otherwise undiscoverable.

Hybrid BGCs are attributed to each component class in clade profiles,
matching how the frontend's filter rail counts them — otherwise the same
BGC would be counted one way in the comparison table and another way in
the sidebar of the same screen.

## Phase 4: publication-grade export

The original brief requires visualizations be "reproducible via
declarative configuration (JSON) and exportable to publication-ready
vector formats (SVG, PDF)." Both halves matter, and the first is the
scientific one.

### The figure carries its own provenance

`ViewConfig` (`engine/src/bgcscape/export/view_config.py`) is a versioned,
validated description of everything that determines what a figure shows —
filters, collapsed nodes, highlighted family, compared clades, search
query — plus **required** dataset provenance: which MIBiG/GTDB/antiSMASH
versions produced the underlying data.

`dataset` is required rather than optional deliberately. A config
recording the filters but not the data versions would be reproducible in
appearance only; the same filters over a newer GTDB release is a different
figure making a different claim.

That config is embedded in the exported SVG as a `<metadata>` element —
part of the SVG spec, ignored by renderers, survives round-tripping
through Illustrator/Inkscape. Six months later, `bgcscape inspect-figure
figure3.svg` answers "which data versions and filters made this?" without
the original session, database, or browser. A visible caption line carries
the same information for readers encountering the figure in print.

### PDF conversion is server-side, deliberately

Browser print-to-PDF varies by browser and platform and silently
rasterizes some SVG features; journals reject raster figures at these
sizes. Converting via cairosvg in the engine gives a deterministic vector
pipeline, and means a figure can be regenerated headlessly (`bgcscape
render-figure`) from the SVG file alone. There's a test asserting the
output contains no `/Subtype /Image`, i.e. that it really is vector.

`/api/v1/export` is the only non-GET endpoint in this API. It isn't a
write — nothing is persisted — but an SVG document doesn't fit in a query
string. cairosvg is a lazy import behind the `export` extra, since Cairo's
system libraries are heavier than everything else in the engine combined.

### Version checking refuses rather than degrades

A config written by a newer Phylo-BGC is rejected outright, not partially
applied. A filter this version doesn't understand would silently change
what the regenerated figure shows — which is exactly the failure this
whole mechanism exists to prevent.

### Two frontend decisions worth recording

**"All classes selected" is recorded as an empty filter list**, not as all
eight class names. The UI's default state is everything-selected, so
recording the full list would make every default export look deliberately
filtered. Empty means "no filter applied", which is what selecting
everything actually means.

**Only font properties are inlined during SVG serialization.** The tree is
styled by Tailwind classes that exist only in the page stylesheet, so an
SVG lifted straight from the DOM renders as unstyled black text elsewhere.
But `fill`/`stroke` are already SVG attributes set by the D3 code, and
copying the browser's full computed style would add hundreds of
irrelevant declarations per node. There are tests asserting the live SVG
in the page isn't mutated by serialization, and that monospace treatment
lands only on the elements that had `font-mono`.

## Phase 5: user uploads and BGC prioritization scoring

### User uploads

`bgcscape ingest upload` reuses the antiSMASH ingestion path but records
`SourceType.USER_UPLOAD` rather than `TOOL_RUN`, so user-contributed data
stays distinguishable from curated reference data at query time. That
distinction is the entire point of the provenance model, and it would be
lost if uploads borrowed the tool-run source type for convenience.
Everything ingested this way is `PREDICTED`, never `OBSERVED_CURATED`.

### Prioritization scoring: three properties, structurally enforced

The original report is explicit that §8 must produce a **prioritization
score**, never a novelty claim. Holding that line meant three design
decisions that constrain the code rather than merely annotate it.

**1. Components are never collapsed into a bare number.**
`PrioritizationResult` always carries its per-component breakdown with a
plain-language explanation each. Every component is a proxy standing in
for something unmeasurable; a rank a user can't interrogate is a rank they
can't disagree with.

**2. Weights are explicit, overridable, and uncalibrated by construction.**
`DEFAULT_WEIGHTS` is deliberately uniform. An unequal default would encode
a scientific claim about which signals matter more — a judgement that
depends on the research question and belongs to the researcher, not this
module. Uniformity is at least an honest statement that no ordering is
being asserted. `WEIGHTS_ARE_UNCALIBRATED` ships in every result's
caveats, and the API returns the weights it used.

**3. Missing evidence is never scored as evidence.**
This is the failure mode that would make the feature actively harmful, so
it gets structural enforcement. If MIBiG has never been ingested, "this
BGC has no close MIBiG relative" is a fact about the database, not the
cluster — and scoring it as maximal distance would rank *every* cluster in
an empty corpus as maximally interesting. Uncomputable components return
`None`, are excluded from the weighted mean (not zeroed, which would
penalize clusters for reference-data gaps; not maxed, which would reward
them for it), and are named in `unavailable_components`. Below two
available components, no score is produced at all — a confident-looking
number derived from one surviving proxy is worse than an honest refusal.

The same principle recurs in the smaller cases: an unclustered BGC returns
`None` for `mibig_distance` because "unclustered" is not the same as
"distant from characterized clusters" — it means the question wasn't
answerable. A genome with no genus-level classification returns `None` for
`class_rarity_in_clade` because there's no peer group to be unusual
relative to. A peer group of one genome likewise returns `None`.

### Everything is relative to the ingested corpus

"Rare" only ever means "rare in this database". `ScoringContext` makes
that dependency explicit by computing corpus statistics once, in one
place, and the result carries a caveat naming the corpus size whenever
it's small enough for that to dominate. This is why the honest answer to
"should we tune the weights?" is that it needs real data at volume first —
weights fitted against a handful of fixture genomes would encode the
fixtures, not the biology.

### What deliberately isn't here

No aggregate metric is exposed anywhere as "novelty". No component
attempts sequence-level divergence or domain-architecture analysis — both
are in the report's §8 sketch, and both need alignment infrastructure
(MAFFT/HMMER) that this project treats as external analysis dependencies
rather than reimplementing. Adding them later means adding components, not
restructuring the scorer; that extensibility is why components are a list
rather than fixed fields.

## Synthetic demo corpus, and what running it at scale revealed

`bgcscape seed-demo` generates ~80 genomes / ~400 BGCs / ~70 families for
evaluating the interface at realistic density. The 5-genome test fixtures
verify ingestion correctness but are useless for judging whether the tree
design works — the genomic-barcode treatment, label crowding, and family
distribution patterns only become assessable at scale.

The data is fabricated, and is constrained to say so: transparently
fictional taxon names (`Pseudostreptomyces demoensis`), `SYN_` accessions
that can't be confused with NCBI assemblies, `evidence_level=HYPOTHESIZED`
throughout, and a source named "SYNTHETIC DEMO DATA (not real)" that
therefore appears in the provenance endpoint, every exported figure
caption, and `inspect-figure` output. Seeding refuses to run into a
database that already holds genomes unless forced.

### It immediately exposed a real methodological flaw

Running the prioritization scorer over 80 genomes, **the entire top of the
ranking was unclustered BGCs** — and not for a good reason. Being
unclustered scores 1.0 on the `unclustered` component *and* makes
`family_rarity`, `taxonomic_isolation`, and `mibig_distance` all
uncomputable at once. So the weighted mean is taken over two surviving
components, both high, and the cluster rises to the top by construction
rather than by evidence.

This was invisible at 5 genomes and would have been invisible forever
without a realistic corpus. It's the clearest argument in this project for
why fixture-scale testing isn't validation.

**Deliberately not "fixed."** Penalizing unclustered clusters or imputing
values for the missing components would both invent evidence, which is the
one thing the scorer refuses to do. The two defensible remedies — rank
within equal-coverage groups, or weight `unclustered` down — are
scientific judgements of exactly the kind this module leaves to the
researcher. So the bias is *named*: any result hitting this pattern
carries an explicit caveat telling the reader the rank is partly an
artifact and to compare it only against similarly-scored clusters.

That's the general principle this codebase keeps landing on: when the
honest answer is a judgement call, surface it rather than pick silently.

## Fixes and visual weighting (post-review)

Three problems surfaced by actually using the tool at 80-genome scale.

### CORS: a bug that 24 passing API tests couldn't see

`allow_methods=["GET"]` was set in Phase 2 when the API was read-only, and
never revisited when `POST /api/v1/export` shipped in Phase 4. The browser
preflight (`OPTIONS`) was rejected with 400, so SVG and PDF export failed
in the UI while every server-side test passed.

The interesting part is *why* it survived: the Phase 4 end-to-end check
called the endpoint with `urllib` from Python, and FastAPI's `TestClient`
doesn't issue preflight requests. So the endpoint was well covered and the
*browser path to it* was not covered at all. There is now an explicit
preflight test. General lesson: testing an endpoint is not the same as
testing how the client actually reaches it.

### Search looked inert because of three compounding failures

Recolouring matched labels to `signal` teal against `ink` body text is
nearly invisible at 12px; a match inside a collapsed clade never rendered;
and at ~150 nodes a hit is usually off the visible scroll. Together these
made a working search read as a broken one. Fixed structurally:

- `effectiveCollapsed()` forces open the ancestor path to every match, so
  hits inside collapsed clades appear. It opens *only* those paths, not
  the whole tree.
- Non-matching branches dim to 15%, so the eye finds hits without needing
  to scan.
- Matches get a highlighter wash (warm amber behind the label), which
  reads at small sizes where a colour swap does not.
- The header shows a match count, so "no matches" is distinguishable from
  "search is broken" — precisely the confusion the original caused.

### Weighted branches

Every branch was a 1.25px hairline carrying no information, which is the
main reason the tree read as thin and diagrammatic. Branch stroke width
now scales with the BGC count of the subtree it leads to, tinted toward
that subtree's dominant BGC class. Visual mass becomes the biosynthetic
signal: thick branches lead somewhere rich.

Details that matter:
- **sqrt scale, not linear.** Counts span ~two orders of magnitude
  (397 at the trunk, 0–13 at tips); linear makes the trunk a slab and
  every tip vanish. Observed result: 11px trunk → 4–9px phyla → 3.5–7px
  genera → 1–2.8px tips.
- **Clamped, not merely scaled.** `branchWidth` was unbounded when a
  node's count exceeded the passed maximum — testing produced a 27px
  branch. Now `Math.min(1, …)`: a rendering bug that draws a slab across
  the figure should be structurally impossible, not dependent on callers
  passing the right maximum.
- **Muted tint (45% opacity).** The branch is context; the BGC tick marks
  carry the precise signal and shouldn't have to compete with saturated
  colour behind them.
- **`dominantBgcClass` returns null on ties.** A tinted branch should mean
  something, and "no clear dominant class" is a real answer rather than a
  reason to pick arbitrarily.

**Deliberately not a Sankey.** A true Sankey needs conserved flow, and
ribbon widths on a phylogeny would compete with branch length for the same
visual channel. This keeps the tree a tree and adds one honest encoding.
The root → phylum → class flow *is* conserved and would make a legitimate
Sankey — but as a separate view, not grafted onto ancestry.

## Tree affordances, and two new views

### Rank badges use D, not K

Each taxon carries a single-letter rank badge — **D**/P/C/O/F/G/S,
matching GTDB's own taxonomy-string prefixes (`d__Bacteria;p__…`). There
is deliberately no K: GTDB's top rank is *domain*, not kingdom, so a K
badge would misdescribe the data this tool actually renders. The badge is
a separate glyph rather than a prefix on the label, so it stays visually
subordinate to the organism name.

### Middle-button pan

Middle-drag pans the canvas; left-drag is deliberately untouched, since
that's how text selection and click-to-select work and hijacking it would
break both. `preventDefault` on mousedown suppresses the browser's
autoscroll cursor.

### Circular / horizontal toggle

Radial layout is the same `d3.tree` algorithm read in polar coordinates —
sized `[2π, radius]`, so `x` is an angle and `y` a radius. Two details
that matter: the radius grows with leaf count (a fixed radius is fine at
20 tips and unreadable at 150), and labels on the left half are rotated
180° and re-anchored, or they render upside down.

### Sankey view: why it's a separate view, not ribbons on the tree

A Sankey requires **conserved flow** — what enters a node must equal what
leaves, or the widths lie. Branch width on the phylogeny already encodes
subtree richness, and a second width channel there would fight it. So the
flow lives in its own view, where `phylum → genus → BGC class` genuinely
is conserved: every BGC has exactly one genome, genus, and phylum.

Verified at 80-genome scale: 397 BGCs in, 397 across the phylum→genus
stage.

**One honest exception.** A hybrid BGC is counted under *each* component
class in the final stage, so an NRPS+PKS cluster appears in both. That
breaks conservation in the last column only (434 = 397 + 37 hybrids). The
alternative — a separate "hybrid" sink — would be formally conserved but
would hide that hybrid clusters *are* NRPS and PKS machinery, and would
disagree with how the filter rail, clade comparison, and branch tinting
all count them. Cross-view consistency was judged worth more than the
invariant, and `hybrid_double_counted` is returned and shown in the UI so
a reader can't infer conservation that isn't there.

Nodes beyond the display cap collapse into an explicit "other" bucket
rather than being dropped — silently omitting flow would make every
downstream width wrong.

### Presence/absence heatmap (report §4.9)

Clade × BGC-class matrix, with the rank selectable from phylum to genus.

**Cell shade encodes clusters per genome, not raw count.** A forty-genome
clade would otherwise look uniformly rich purely for being better sampled,
which is sampling effort rather than biology. The raw count is still
printed in the cell, because the rate alone can't tell you whether it
rests on one genome or forty — and each row shows its genome count for
the same reason.

The absence caveat is returned by the API and rendered above the grid: an
empty cell means no genome *in this dataset* was found to carry that
class, not that the clade lacks it. Same reasoning as
`only_in_this_clade` in the comparison endpoint.

## Radial canvas fixes

### BGC ticks pointed inward on the left hemisphere

`GenomeNode` wrapped its *entire* group in `rotate(180)` for left-half
nodes. That correctly flipped the label so it reads left-to-right, but it
also flipped the BGC tick marks — and in the parent frame (`rotate(angle −
90) translate(radius, 0)`) the `+x` direction is radially **outward**
regardless of hemisphere. So on the left half the barcode grew back toward
the hub, crossing the branches.

Fixed by scoping the flip to the label only: the ticks now stay in the
unflipped frame at `+x`, which is outward everywhere. The general lesson
is that in a radial layout, "flip the label so it reads correctly" and
"mirror the geometry" are different operations, and a group transform
does both.

### Zoom and pan

`d3.zoom` on the SVG, transform applied to a wrapper `<g>` (not the `<svg>`
itself, so exported SVG geometry stays in figure coordinates). Wheel zooms
about the cursor; middle-drag pans.

The zoom filter deliberately excludes left-drag: that is click-to-select
and shift-click-to-compare, and `d3.zoom` would swallow both. Middle-drag
also gets an explicit `preventDefault` to suppress the browser's autoscroll
cursor.

### Label overlap: semantic zoom, not smaller type

In a radial layout the space for a label is an *arc*, so it shrinks toward
the centre and with every added leaf. Inner taxon nodes are the worst case
— dozens of siblings sharing a small circumference. Two changes:

**Radius is now derived, not guessed.** It comes from the arc each leaf
needs (`r = leafCount × ARC_PER_LEAF / 2π`), so the outer ring keeps its
spacing as leaves multiply instead of packing tighter into a fixed circle.
A minimum radius floors it, which means sparse trees get *more* than the
minimum spacing — fine, since the failure mode being guarded against is
crowding, not generosity.

**Labels render only when their own arc can hold them**, scaled by the
current zoom — the approach iTOL and Krona take. Zooming in progressively
reveals labels rather than magnifying an unreadable tangle. At 80 genomes:
leaf labels show at 1×, crowded inner nodes appear by ~4×. Anchor ranks
(domain/phylum/class) always render: there are few of them, they carry
orientation, and losing "Bacteria" to a spacing rule would be worse than
slight overlap.

A counter reports how many labels are withheld, so hidden labels read as
"withheld for space" rather than missing data — the same confusion the
search fix addressed.

### An unrelated bug this surfaced

The frontend test count dropped from 63 to 52 without any test being
deleted. `jsdom` had been installed with `--no-save` in an earlier chunk
and was later pruned, so `export.test.ts` (15 tests) failed to collect —
and **vitest still exited 0**, reporting the remaining file as passing. A
silently shrinking suite is worse than a failing one. `jsdom` is now a
saved devDependency; 67 tests run.

## Rank-level collapse control

A left-rail control ("Show down to…") sets the whole tree's depth in one
click: Domain → Phylum → Class → Order → Family → Genus → Species →
Genomes. On the 80-genome corpus this steps the visible node count
2 → 5 → 9 → 13 → 19 → 26 → 78 → 158.

This matters more than a convenience: on a dense tree, the node you want
to collapse is frequently not on screen, so per-node clicking is a poor
way to control depth.

Three decisions worth recording:

**Genomes is the deepest level.** BGCs render as tick marks *on* a genome
rather than as tree nodes, so there is no BGC level to collapse to — they
appear or don't with their genome. The control says so rather than
offering a level that couldn't work.

**Skipped ranks terminate the branch anyway.** Real taxonomies omit
ranks — a genus can sit directly under a family with no order between.
`collapseToLevel` collapses every taxon at or *below* the target depth,
not only exact rank matches, so a branch missing the requested rank
becomes a leaf at the shallowest rank it does have. Showing one rank
deeper than asked is better than the alternative (matching on rank
equality alone would leave such a branch fully expanded while its
siblings collapsed).

**Only the topmost node of a branch is collapsed**, not every descendant.
Collapsing nodes beneath an already-collapsed one is redundant and would
leave stale keys behind when the user re-expands by hand.

Manual toggling clears the active level highlight, since the tree no
longer matches the preset and leaving it lit would claim a depth that
isn't true. Levels absent from the loaded dataset are disabled rather
than offered as no-op buttons — `ranksPresent()` derives that from the
data instead of assuming the full seven-rank hierarchy exists.

## First contact with real data

2,745 real MIBiG entries were ingested from `mibig-secmet/mibig-json`.
The parsers had been written against formats read from the tools' own
source, and this was the test of whether that survives reality.

**It did not, in one important way — and that was the point of doing it.**

### The bulk repository ships a different schema than the website

MIBiG 3.x, not the 4.0 the parser targeted: payload nested under
`cluster`, `mibig_accession` instead of `accession`, `biosyn_class` as a
flat list, `loci` as a single object, `ncbi_tax_id` as a *string*, and a
different class vocabulary naming the product ("Polyketide", "NRP")
rather than the machinery ("PKS", "NRPS"). Both schemas are live, so the
parser now detects and handles both rather than picking a side. Full
field mapping in `docs/DATA_SOURCES.md`.

Two edge cases only real data produced: **half-present coordinates**
(1,408 entries have `start_coord`, 1,407 have `end_coord` — a start
without an end implies a span that isn't known, so both are dropped), and
**non-numeric tax IDs**, which now degrade to null rather than raising.

Result: 2,526 active entries ingested in 23s with zero errors, 219
retired/pending correctly skipped, 4,196 real compounds linked.

### MIBiG alone is not a tree

The structural finding. MIBiG records `organism_name` and `ncbi_tax_id` —
a species and nothing above it. Ingested alone it yields **1,527 species
nodes directly under the root, maximum depth 1**. GTDB is what supplies
the hierarchy; the two sources are complementary, and the Phase 1b
cross-source merge is what joins them.

### The scoring guarantee held under real conditions

On MIBiG-only data the prioritization scorer returned **no score at all**
for every cluster — 1 of 5 components computable (no families ingested,
so three are undefined; no genus-level taxonomy, so the fourth is too).

This is the missing-evidence guarantee doing exactly its job on data it
had never seen: rather than emitting a confident number derived from one
surviving proxy, it declined and explained which components were missing
and why. That property was designed against a hypothetical; this is the
first evidence it survives contact with a real corpus.

### Performance at 6x the synthetic scale

2,526 BGCs: taxonomy-tree 0.87s (959 KB), flows 0.44s, heatmap 0.42s,
prioritization 0.84s. Acceptable, but the 959 KB tree payload and 1,527
sibling nodes are the first sign that the in-memory tree builder and the
"render every node" frontend will need the CTE/virtualization work both
have been flagged for since Phase 2.

## Pruning to BGC-bearing genomes

A real GTDB ingest brings in every genome in the release, but only the
ones antiSMASH has been run on carry BGCs. On a 3,000-genome GTDB corpus
the tree rendered 4,659 nodes of which almost all were empty scaffolding —
pruning to BGC-bearing genomes leaves 9. That is the difference between an
unusable tree and a readable one, so **pruning is the default** and the
full tree is the opt-in.

Four decisions:

**The check is O(1) per node.** `subtreeHasBgcs` reads the rolled-up
`bgc_class_counts` the API already computes rather than walking the
subtree. This runs on every render, and a walk-per-node would make
pruning cost more than it saves.

**`genome_count` is recomputed on the pruned tree.** Branch weighting,
level collapse, and the header all read it; leaving the pre-pruned value
would have them describing a tree that isn't on screen.

**Empty results fall back to the full tree.** If nothing anywhere carries
BGCs — GTDB ingested without antiSMASH, which is a normal intermediate
state — pruning would produce a blank canvas that reads as a broken app
rather than an empty result. The fallback is explicit, and the UI says
why and names the command that would populate it.

**The header reports "N of M genomes", not a bare count.** A filtered
tree that doesn't announce itself is indistinguishable from missing data —
the same failure the search fix addressed. The rail states how many
genomes are hidden and that they remain in the database.

### A typechecking gap this surfaced

`tsc --noEmit` passed on a test file with a missing type import that
`next build` then rejected. The two run different configurations, so
`npm run typecheck` is not a substitute for building before shipping.

## Navigating at scale: summary glyphs and focus mode

A global tree of everything is never what a researcher arrives wanting.
They come with a question — *where does my MAG sit?*, *what's the closest
characterized relative?*, *which lineages are worth bioprospecting?* — and
none of those need every tip drawn. Rendering faster wouldn't help; a
500,000-node tree is uninterpretable at any framerate. The fix is to draw
**less, but more meaningfully**.

### Collapsing now summarises rather than hides

A collapsed clade renders as a glyph: width encodes genome count (sqrt
scale, clamped, for the same reason branch widths use it), filled with a
stacked bar of its BGC class composition, labelled `Ng · Nb`.

This inverts the previous behaviour. Zooming out used to *remove*
information, which is exactly why a large tree felt uninformative; now a
phylum-level view is a handful of richly-loaded objects instead of a
handful of dots. On a 3,000-genome GTDB-shaped corpus: **4,659 objects at
full expansion, 11 at genus level** — and those 11 carry composition, not
just position.

Composition is ordered largest-first so the dominant segment is always
leftmost and glyphs are comparable across clades at a glance. A clade with
no clusters renders as an outline rather than a filled bar, so "empty" is
visibly different from "not drawn".

### Focus mode

Double-click any clade to re-root the view on it; breadcrumbs climb back
out. Navigation becomes drilling rather than scrolling, so the number of
objects on screen stays bounded regardless of corpus size.

Double-click rather than single: single click is collapse and shift-click
is compare, both more frequent. Focusing also force-expands the target,
since re-rooting onto a collapsed node would otherwise render a single
glyph with nothing beneath it.

`applyFocus` falls back to the full tree when the focused clade is no
longer present — which happens legitimately when the BGC-bearing filter
prunes it away. Blanking the canvas would read as a crash; instead the
breadcrumb bar explains what happened.

### What this does not fix

**MIBiG-only data is flat.** All 1,527 species are direct siblings of the
root, so collapse levels, glyphs, and focus have no hierarchy to work
with — every level shows the same 1,528 objects. This isn't a limitation
of the new features; it's the same finding as before, seen from another
angle: GTDB is what supplies the tree structure, and MIBiG without it is a
fan rather than a phylogeny.

**Payload size is untouched.** The full tree is still fetched and pruned
client-side. At real GTDB scale that becomes the binding constraint, and
the fix is server-side lazy aggregation (`/tree?root=X&depth=2`) — a
larger change, and the next one worth making before going live.

## Genome-level detail and filtering (Chunk A)

### Node size encodes BGC count

Five tiers (0 / 1–5 / 6–20 / 21–50 / >50) rather than a continuous scale:
the distinction that matters is categorical — worth looking at or not —
and a smooth ramp makes every genome look mid-range.

BGC-negative genomes are **muted, not removed**: smaller, grey, 65%
opacity, but still drawn. They are evolutionary context, and deleting
them from the tree would misrepresent the phylogeny. The node is also
tinted by its dominant BGC class, so a tip's colour and size together say
"how much, and of what" before any label is read.

### Filters are limited to what the model can answer

BGC count range, MIBiG matched/unmatched, genome size, GC content,
minimum completeness, MAGs only. Every one is backed by a real column —
a filter the database can't answer silently returns nothing and reads as
a bug.

Two behaviours worth stating:

**A missing measurement passes rather than fails.** A genome with no
recorded GC content shouldn't vanish because a GC filter is set; the
filter simply can't speak to it. Treating null as a failed comparison
would quietly hide exactly the incompletely-annotated genomes a
researcher most needs to see.

**Filtering everything out falls back to the unfiltered tree**, with an
explanation — the same reasoning as the BGC-bearing filter and focus
mode. A blank canvas reads as a crash rather than an empty result.

Genome metadata (`genome_size_bp`, `gc_content_pct`, `completeness_pct`)
now rides in the tree payload so filtering needs no request per genome.
That is a real payload cost, bounded and small per genome; Chunk B's lazy
aggregation is what actually addresses payload size.

### Genome panel: tabs, lineage, external links

Overview / BGCs / Genome / Lineage, plus a taxonomy breadcrumb and a
status dot. Overview shows the first six clusters with a "show all"
affordance; the BGCs tab shows everything.

`lineage` is assembled server-side by walking `Taxon.parent_id` (with a
cycle guard) and returned root-first, because the tree payload carries
only a genome's own taxon — reconstructing ancestry client-side would
need the whole taxon table.

The Lineage tab explains its own emptiness on MIBiG-only data rather than
rendering blank: MIBiG records a species and nothing above it.

**External links are generated from the accession, and antiSMASH DB is
deliberately omitted.** NCBI and GTDB resolve for any assembly accession;
antiSMASH DB only resolves for genomes that happen to be in it, and a
link that 404s for most genomes is worse than no link.

### The donut agrees with everything else

`/api/v1/bgc-type-counts` attributes hybrids to each component class,
exactly as the filter rail, comparison, heatmap and Sankey do. A donut
disagreeing with the sidebar beside it would be worse than no donut. Its
total (434 on the demo corpus) therefore matches the Sankey's final
column rather than the raw BGC count (397) — the same documented
hybrid double-count.

## Chunk B: incremental tree loading

`/api/v1/taxonomy-tree` builds the whole hierarchy in memory and ships it
in one response. That was a deliberate MVP simplification and it held to
~2,500 BGCs at ~1.1 MB. It would not survive a real GTDB release:
~600,000 genomes is a payload no browser should parse, for a tree no human
can read anyway.

`/api/v1/tree?root=X&depth=N` serves one slice at a time. Measured:

| corpus | eager | lazy (depth 1) |
|---|---|---|
| MIBiG, 2,526 BGCs | 1,116 KB / 1.36s | **<1 KB / 0.51s** |
| GTDB-shaped, 3,000 genomes | 871 KB / 0.84s | **<1 KB / 0.16s** |

### The property that makes shallow loading usable

**Rolled-up counts cover the whole subtree, not the returned slice.** At
depth 1 the root has fetched no children but still reports 3,000 genomes
and every BGC class count beneath it. If counts only covered what was
returned, every summary glyph would understate its clade and the feature
would be actively misleading rather than merely incomplete.

This is what makes a shallow response a *view* rather than a loading
state: combined with the collapsed-clade glyphs, depth 1 is a legible
summary of the entire corpus.

`truncated_at` names the nodes where expansion stopped, so a client can
place "expand" affordances precisely instead of guessing.

### Two bugs the tests caught

**Genomes were gated on depth.** They attached only at the deepest
*requested* level — so a shallow request returned none at all whenever
the taxonomy placed genomes deeper than that. Depth governs *taxon*
recursion; genomes are leaves, and the size cap is what bounds them.

**`MAX_DEPTH` was too low to reach species.** GTDB is seven ranks and the
synthetic root sits above them, so reaching species needs 8; the original
6 silently made the deepest level unreachable. Caught by a test asking
for genomes at `MAX_DEPTH` and getting none because recursion stopped at
family.

### Deliberately not done

**The eager endpoint stays.** Export needs a complete figure, and the
existing frontend consumes it; removing it to prove a point would break
both. The two coexist, with the lazy one as the path that scales.

**The rollup pass is still in-memory.** Counts are computed over the whole
taxonomy on every request, which is the remaining bottleneck — a
recursive SQL CTE is the obvious next optimisation. Not bundled here so
the API-shape change can be evaluated on its own; shipping both at once
would make a regression in either hard to attribute.

**The frontend still uses the eager endpoint.** Porting it is a real
piece of work (incremental fetch-on-expand, cache invalidation, focus
interaction) and belongs in its own chunk rather than tacked onto the API
change.

## Two kinds of grouping, and the regression that made the distinction typed

`bgc_family` holds two scientifically different objects, and for one release
it could not tell them apart.

- A **sequence family** is a BiG-SCAPE / BiG-SLiCE Gene Cluster Family:
  clusters grouped because their gene content and domain architecture are
  similar. Produced by a real clustering run over cluster sequences.
- A **compound group** is a set of clusters MIBiG records as producing the
  same named compound. A curated experimental fact — and no sequence
  comparison anywhere in it.

`bgcscape group-by-compound` wrote the second kind into the same table as the
first, distinguished only by the free-text `clustering_method`. The
prioritization scorer did not look at that field. It therefore read compound
groups as sequence families, and three of its five components —
`unclustered`, `family_rarity`, `taxonomic_isolation` — began emitting
sequence-similarity claims about a corpus on which no clustering had ever
been run.

The effect, measured on the real data:

| corpus | refused to score (before) | refused (after) |
|---|---|---|
| MIBiG-only, no groups | 2,437 / 2,437 | 2,437 / 2,437 |
| MIBiG-only **+ compound groups** | **0** | **2,437** |
| GTDB + MIBiG (no groups) | 783 | 783 |
| **shipped bundle** (GTDB + MIBiG + groups) | **0** | **783** |

Running `group-by-compound` — a step in the shipped build — turned the
missing-evidence guarantee off for the entire corpus. Every cluster received a
confident number, and the explanation attached to the top-scoring ones read
"Not assigned to any gene cluster family — no sufficiently similar cluster was
found in this corpus", which was simply false: nothing had been compared.

### The fix is a typed column, not a string check

`BGCFamily.kind` is a CHECK-constrained enum (`FamilyKind`). The scorer filters
every family-derived component through `sequence_memberships()`, and
`families_present` now asks "has a *sequence* clustering been ingested?" rather
than "does this table have any rows?".

A string comparison against `clustering_method` would have fixed the symptom.
It would not have stopped the next tool that writes a third kind of grouping
from silently joining the pool. The column makes the question unavoidable at
the point a row is created, and the constraint makes an unclassified row
impossible to insert — including from outside the ORM.

Compound groups are still first-class: they are served by `/api/v1/families`,
labelled in the UI, and reported in the scorer's corpus-level caveats as
deliberately excluded. Excluding them silently would have been its own kind of
dishonesty.

### Product categories are flagged, and the flag was itself wrong

`GENERIC_PRODUCT_NAMES` marks compound groups keyed on a product *category*
("carotenoid", "capsular polysaccharide") rather than a molecule. Grouping on
one says "both make some carotenoid" — much weaker than "both make the same
compound", and the four largest groups in the bundled corpus are exactly these.

`is_generic_product()` existed to flag them and was **never called** — verified
at runtime, not by grep: wrapping the function and running a full
`group_by_compound` over 279 groups plus an API serve of all of them produced
zero invocations. It was also wrong. `_label_for` slugifies to
`CMPD_o-antigen`; the old inverse mapped hyphens back to spaces, producing
"o antigen", which is not in the vocabulary. Wiring it up unchanged would have
looked like a fix while still missing the one hyphenated name — an 11-member
group in the real corpus. Membership is now tested label-to-label, and the
round trip is asserted for every name in the set.

## Absence needs a denominator: `AnalysisRun`

The data model recorded what we believe. It did not record what was
examined, by what, with what coverage — and three of this project's worst
claims traced to that single gap.

A genome with no BGCs and a genome nobody had ever run antiSMASH on were the
same row. Both had zero `bgc` children; both rendered as "0 BGCs". On a full
GTDB ingest that is hundreds of thousands of organisms the tool asserts
produce nothing, having never looked at one of them. It was the falsest
thing this tool said, and it said it confidently, in a count.

`AnalysisRun` + `AnalysisRunCoverage` (models/analysis.py) record which tool,
which version, which parameters, which genomes, when. `bgcscape.coverage`
turns that into the question every caller actually has:

| state | meaning | what absence licenses |
|---|---|---|
| `EXAMINED` | a `BGC_DETECTION` run covers this genome | zero clusters is a **finding** |
| `CURATED_ONLY` | clusters recorded, no covering run | the count is a **floor**, not a census |
| `UNEXAMINED` | no run, no clusters | nothing. Nobody looked. |

### Why this is not `Source`

`Source` documents itself as "one specific antiSMASH/BiG-SCAPE execution",
so the overlap deserves an answer. In practice it is not one:
`_get_or_create_source` keys on `(name, version)`, so a single `Source` row
covers *every* antiSMASH 7.1.0 run ever ingested here. And `Source` names no
genomes — which is the entire point. An `AnalysisRun` points at a `Source`
rather than replacing it.

### Coverage is typed, and MIBiG creates none

`analysis_type` is required because "covered by BiG-SCAPE" says nothing about
whether anything looked for clusters, and "covered by antiSMASH" says nothing
about whether its clusters were ever compared. Those are two different
denominators and the scorer needs them apart.

MIBiG ingestion deliberately records **no** run. A MIBiG entry is a curated
report that one cluster exists in an organism; it is not a survey of that
organism's genome. Recording detection coverage for it would manufacture
exactly the denominator this table exists to stop assuming — it would turn
"somebody once published three clusters" into "we looked and found three".

### What that says about the shipped corpus

All 2,437 clusters in the bundled database are MIBiG, `predicted_by_tool` is
NULL for every one, and no antiSMASH run exists anywhere in it. So after this
change the bundle reports, correctly:

```
Genomes: 1542
  examined            0
  curated only     1521
  unexamined         21
```

Zero examined. That is uncomfortable and it is true, and the interface
states it **once**, at corpus level, rather than by greying out every glyph —
on a corpus with no coverage that would read as a broken app rather than an
honest one. The tree marks unexamined empty clades with a hatch and a dashed
outline; examined-empty clades keep the hollow rectangle, which now means
something.

### `record-analysis-run` exists for the half that has no output

antiSMASH over 900 genomes finding clusters in 40 produces 40 files. The
other 860 are the scientifically interesting half — genomes examined and
found empty — and no ingestion path can see them, because they produced
nothing to ingest. `bgcscape record-analysis-run` declares that coverage, at
`evidence_level = HYPOTHESIZED` rather than `COMPUTED`: Phylo-BGC did not
read a tool's output to establish it, somebody asserted it. Both are worth
having; they are not equally strong, and a query can tell them apart.

## The scorer's denominators were "rows somebody loaded"

Every rarity component is a fraction, and the denominator was whatever
happened to be ingested. A class occurring in 1 of 40 curated entries is not
"rare in this clade" unless those 40 genomes were surveyed — and the genomes
MIBiG has entries for were not surveyed, they were *published about*.

Two corrections, both in `scoring/prioritization.py`:

**`class_rarity_in_clade`** now counts only clusters on detection-covered
genomes, over the peer group's **examined** genomes, and returns `None` below
two of them. Numerator and denominator come from the same population; letting
curated entries into the numerator made a clade look unusual in proportion to
how much literature it has.

**`unclustered`, `family_rarity`, `taxonomic_isolation`** are answerable only
for genomes a `SEQUENCE_CLUSTERING` run reached. This fixes a bug that was
dormant only because no clustering had been ingested: `families_present` was
corpus-wide, so one BiG-SCAPE run over ten genomes would have made every
other cluster in the corpus score 1.0 on `unclustered` — *"no sufficiently
similar cluster was found"* — having never been compared to anything.

Every caveat now names its denominator, prefixed `DENOMINATOR:`.

### One derivation holds, and only in one direction

A genome carrying a BGC in a sequence family was demonstrably in a clustering
run — the membership *is* that run's output. So clustering coverage is
derived from memberships as well as from `AnalysisRun`, which keeps a corpus
clustered before this change answering correctly. The reverse does not hold
and is not assumed: no memberships tells you nothing about whether the genome
was compared. And detection coverage is **never** derived, for the MIBiG
reason above.

### The consequence, stated plainly

| corpus | scored before | scored after |
|---|---|---|
| shipped bundle (GTDB + MIBiG + compound groups) | 2,052 of 2,437 | **0 of 2,437** |
| synthetic demo (80 genomes, coverage recorded) | all | all |

The bundle's 2,052 scores were the artifact. With `class_rarity_in_clade`
correctly unavailable, only `mibig_distance` remains computable, which is
below `MIN_COMPONENTS_FOR_SCORE` — so the scorer declines, exactly as it does
on any other MIBiG-only corpus. This is the same refusal ARCHITECTURE.md's
own "MIBiG-only, no groups: 2,437 / 2,437" row always described; the corpus
was only escaping it by counting curated clusters as a survey.

> **Superseded as a description of the shipped bundle.** The `0 of 2,437` above
> is what this pass correctly produced *at the time*, on a corpus with no
> sequence clustering in it. A real BiG-SCAPE run has since been ingested, and
> 1,227 of 2,437 clusters now score — see "'Same BGC' finally has a sequence
> meaning" below. The refusal reasoning is unchanged; only the evidence
> available to it is.

## Placement is a relation, not a JSON blob

`link-mibig` re-points each MIBiG cluster onto GTDB's genome for the same
organism. That inference lived in a `_bgcscape_placement` key inside
`BGC.raw_annotation`: real, but unqueryable and unconstrained. "Which entries
rest on weak name matching?" meant decoding 2,437 JSON blobs in Python, and
nothing stopped a caller writing a method string the vocabulary never had.

`bgc_organism_placement` (models/placement.py) stores `method`, `confidence`
and `caveat` as columns. On the bundle:

| confidence | count | methods |
|---|---|---|
| strong | 1,589 | `ncbi_taxid` |
| moderate | 40 | `gtdb_species` (31), `ncbi_species_taxid` (9) |
| **weak** | **220** | `ncbi_species_name` |

`WHERE confidence = 'weak'` — 220 clusters whose position on the tree is
nomenclature rather than an identifier. `bgcscape placements --confidence
weak` lists them.

### The claim is carried by the column name

The FK is `representative_genome_id`, not `genome_id`. The genome *represents
the organism*; it is not the assembly the cluster was sequenced from, and the
column name is the only place a reader is guaranteed to look. `BGC.contig`
still holds MIBiG's own locus accession, so what was actually sequenced
remains recorded, and every non-unplaced caveat says "NOT sequenced from this
assembly" in as many words.

An undefined `match_method` is **counted and skipped**, never coerced. The
mapping TSV's method column is free text from a script somebody can edit;
inventing a confidence for a value nobody defined would put a number on the
tree that no method backs. The cluster is still linked — only the confidence
claim is withheld.

### The migration's backfill, and the bug real data found

`b8c2d5e71a30` lifts every placement out of `raw_annotation` into the table —
1,849 rows on the bundle. It also keeps writing the JSON key, deliberately:
the downgrade drops the table, and the JSON is what a downgraded database
still has. `placement_of()` reads the table and falls back to the JSON, so a
database migrated but not re-linked still answers.

The backfill shipped a real bug that the empty-database round trip could not
see, because an empty database has no rows to insert. `sqlalchemy.Uuid`
stores as native UUID on Postgres and CHAR(32) on SQLite, so ids read back by
raw SQL are `uuid.UUID` on one dialect and `str` on the other; feeding the
string into a `sa.Uuid` bind parameter fails with `'str' object has no
attribute 'hex'`. Found by running the migration against the real 2,437-cluster
bundle. Verified afterwards on **both** dialects with seeded placement rows,
not just on the empty schema.

## Two kinds of grouping: the last three consumers

`BGCFamily.kind` landed in `725aba2` and the scorer has honoured it since.
Three consumers still pooled the two:

- **`api/comparison.py`** counted both into one `family_count` and one
  `shared_families` list, so two clades sharing a compound group read as
  sharing repertoire. Every `FamilyRef` now carries its `kind`, the per-clade
  counts are split, and a caveat says why the difference matters: convergent
  evolution routinely produces the same molecule from unrelated pathways.
- **`/api/v1/provenance`** summed both into `family_count`, the number that
  travels into figure captions. Split.
- **The BGC detail panel** labelled every `family_id` "Gene cluster family"
  and offered to show "this family's distribution" — on a MIBiG-derived
  corpus that is 100% compound groups, so it offered shared gene content and
  delivered shared chemistry. It now labels each by kind and changes the verb.


## `is_mag` was a boolean with no source

Every ingest path in this project wrote `is_mag=False`, and not one of them
had grounds for it:

- `ingest/gtdb.py` set False with the comment *"no verified MAG-detection
  column yet"* — an admission in the code that the value was a placeholder;
- `ingest/mibig.py` set False on a deposited **locus**, which is not an
  assembly, so neither answer applies;
- `ingest/antismash.py` set False from a JSON carrying no assembly metadata
  at all, and its comment named this exact gap as unfixable in the schema.

The detail panel read the column and rendered **"Isolate genome assembly"**
for all 1,542 genomes in the shipped corpus — a claim about each genome's
provenance, made on nothing. `AssemblyLevel.UNKNOWN` had existed since Phase
1b for precisely this reason; `is_mag` simply never got the same option.

It is now `bool | None`. False means *established as not a MAG*; None means
the question has never been answered. Migration `c9f1a4d83b57` nulls every
unverified False, keeping the one signal that is real: a row already at
`assembly_level = 'mag'` becomes True, because that level is parsed from
GTDB's own metadata. On the bundle: 1,542 unverified Falses to NULL, none
promoted (GTDB's metadata emits no MAG level for these genomes).

The downgrade cannot preserve the distinction — a NOT NULL boolean has
nowhere to put a third value — so it re-asserts False and says so in its
output rather than losing the fact quietly.

`magOnly` in the filter rail now requires `is_mag === true`, so an
unestablished genome is excluded for want of an answer rather than counted
as an isolate, and the panel says which.

## Interface gaps that were engine features with no front door

Three capabilities were complete, tested and unreachable.

**Prioritization had no UI at all.** The scorer, the API and
`bgcscape prioritize` all worked; nothing in the frontend called them.
`PrioritizationPanel` closes that, and its design problem is worth
recording: **a refusal is this engine's most important output, and a ranking
UI is the natural place to hide one.** After the denominator work the scorer
declines every cluster in the shipped corpus, so a panel that listed only
scored rows would render an empty list where the engine had said something
precise. Unscored rows are therefore first-class — listed, counted, each
naming the components that could not be computed — and the corpus caveats
sit *above* the list rather than folded under it, because they govern how
every row in it reads.

A bug worth keeping: the panel first shipped guarding its fetch on the
`loading` state, which put `loading` in the effect's dependency array. So
`setLoading(true)` re-ran the effect, fired the previous run's cleanup, set
`cancelled = true` on the request still in flight, and discarded its result.
The panel sat on "Scoring the corpus…" forever against an endpoint answering
in 0.9 s. Caught by opening it in a browser, not by a test — the same lesson
this file keeps recording.

**The class filter rail could silently omit a class.** It iterated
`CLASS_ORDER`, the keys of the hardcoded palette in `colors.ts`. A class the
corpus contains but the palette does not was counted by `countBgcClasses`
and then never rendered: no row, no toggle, no way to see or filter its
clusters. `BGCClass` is deliberately an open vocabulary — that is why
`native_enum=False` was chosen — so the rail now asks `/api/v1/bgc-classes`
what exists and appends anything the palette lacks in grey, saying so.

**Search read only the loaded tree.** That remains the primary: it matches
compound names, MIBiG accessions and cluster classes, none of which the
`/search` endpoint covers. But the tree is pruned to BGC-bearing genomes by
default and scoped to one taxonomy, so a genome genuinely in the database
could match nothing and read as "no matches" — the same failure the match
count was added to fix, one level further out. When and only when the tree
has zero hits, the header now reports how many records the database holds
for that query.

## Uploads do not survive a redeploy, and now say so

A hosted deployment writes to a container filesystem that is replaced on
restart. The upload dialog reported placement in full detail and implied
persistence by saying nothing about it. Render's free tier has no disk to
attach, so the honest fix is the notice, not a config change: the result
panel now leads with the fact that the upload is temporary and names the two
ways to keep the data.

## Provenance is only structural if it is populated

Every `Source` in every shipped build had `license`, `url`, `citation` and
`retrieved_at` set to NULL. The model had the columns and
`docs/DATA_SOURCES.md` had the values; nothing carried one to the other.

That is not cosmetic here. GTDB ships under **CC BY-SA 4.0**, a ShareAlike
licence that obliges any derived view to carry attribution — and Phylo-BGC's
derived view is an exported figure destined for a paper. The figure attributed
nothing. `SOURCE_METADATA` in `cli/main.py` now populates these on every
ingest, backfilling existing rows, so re-ingesting is what repairs an old
database.

Relatedly: `group-by-compound` typed its Source as `REFERENCE_DATABASE`,
claiming MIBiG had published the grouping. It is `TOOL_RUN` — Phylo-BGC derived
it. That claim travelled into the provenance block of every exported SVG, which
is the archival record.

## Re-ingestion must not undo placement

`ingest mibig` then `link-mibig` then `ingest mibig` is the documented "new
MIBiG release" workflow. It used to destroy the corpus.

MIBiG entries arrive with a locus accession, not an assembly, so ingestion
creates a stub `Genome` at `AssemblyLevel.LOCUS`. `link-mibig` then moves each
cluster onto the GTDB genome of the same organism and deletes the emptied stub.
Re-ingesting recreated the stub and pointed the cluster back at it. Measured on
the real corpus: **1,629 clusters moved off real GTDB assemblies back onto
locus stubs** (0 left on a real assembly), 1,504 stub genomes resurrected, 665
orphan species nodes regrown, 4 duplicate species created — while the report
line said `created=0, updated=2437`, i.e. perfectly idempotent. Row counts, not
the report, are what caught it.

The invariant now enforced in `load_mibig_entry`: **if a cluster already sits
on a genome that is not its own MIBiG locus stub, something placed it
deliberately and ingestion leaves it alone** — including the species node the
stub hung from. A cluster that was never linked still gets its stub, so a
genuine new release ingests normally.

The general lesson, and the reason this is recorded rather than just fixed: an
ingest report counts the records it was asked to process. It says nothing about
rows it creates as a side effect. Idempotency claims in this project are
verified by row count.

## Alembic autogenerate cannot be trusted with CHECK constraints

Documented twice before as "read the migration first". It is now mechanical.

Alembic reports every named CHECK constraint as *removed* and emits a drop for
it while recreating none — **with no model changes at all**, on both SQLite and
Postgres. Applying one such migration took the schema from 12 CHECK constraints
to 1 and made an invalid `source_type` insertable by raw SQL, undoing the Phase
1b fix entirely.

`include_object` in `migrations/env.py` now excludes CHECK constraints from
autogenerate comparison. These constraints are owned declaratively by the enum
columns, so autogenerate has no business diffing them; a genuine vocabulary
change is hand-written, which was already the rule. With the hook in place,
autogenerating against an at-head database emits `pass` on Postgres and only
the real diff on SQLite. `test_autogenerate_excludes_check_constraints` pins
the behaviour, and `test_enum_check_constraints_are_enforced_by_the_database`
asserts the protection itself with a raw-SQL insert.

## Where the API's time actually went

Profiled rather than guessed, on the 2,437-BGC bundle.

`build_taxonomy_tree` spent **41% of its CPU in `json.decoder.raw_decode`** —
0.34s of 0.82s. The cause: it loaded `Genome` and `BGC` as mapped ORM objects,
and `BGC.raw_annotation` is a JSONVariant holding the entire original MIBiG
record. SQLAlchemy dutifully deserialised ~4,200 blobs per request to build a
tree that never reads them. The heatmap, the Sankey flows and the type-count
donut all did the same thing.

Selecting scalar columns instead of mapped objects removes both the JSON decode
and the ORM instrumentation overhead. Payloads are byte-identical.

| endpoint | before | after | payload before | after |
|---|---|---|---|---|
| `/api/v1/taxonomy-tree` | 0.662 s | 0.149 s | 1,125,672 B | 230,686 B |
| `/api/v1/tree?depth=1` | 0.587 s | 0.087 s | 338 B | 338 B |
| `/api/v1/tree?depth=2` | 0.606 s | 0.127 s | 258,821 B | 47,978 B |
| `/api/v1/heatmap?rank=genus` | 0.432 s | 0.061 s | 191,659 B | 23,881 B |
| `/api/v1/flows/taxonomy-class` | 0.457 s | 0.065 s | 7,126 B | 1,070 B |

Two findings worth keeping:

**The lazy endpoint was not faster than the eager one.** `/tree?depth=1`
returned 338 bytes and still cost 0.587s, against 0.662s for the entire 1.1 MB
tree. Payload was never its bottleneck — the full-taxonomy rollup on every
request was, and it was paying the same ORM cost. Porting the frontend to
incremental loading would have bought almost no latency until that was fixed.
It is fixed now, and the lazy path is genuinely 6.7x faster, which is what
makes that port worth doing when the corpus outgrows the eager payload.

**Response compression was simply absent.** The tree payload is deeply
repetitive JSON; gzip takes 1.10 MB to 0.24 MB. One middleware line.

Heatmap row order also gained an explicit tiebreaker. It sorted on
`-genome_count` alone, so equal-count clades came out in whatever order the
database returned their genomes — stable within one build, not across dialects
or after an unrelated ingest. A figure's row order should not depend on that.

## Interaction cost is reconciliation, not DOM writes

The tree renders 3,528 nodes on the bundled corpus. The pan/zoom transform was
held in React state and applied through JSX, so **every mouse-move during a pan
re-rendered the whole canvas** to change one attribute on one `<g>`.

The transform is now written straight to the DOM in the d3 zoom handler. Scale
stays in React state, because label visibility is semantic-zoom dependent, but
it is quantised: panning never changes `k` and therefore renders nothing, and a
continuous wheel gesture renders a handful of times instead of once per event.
A `useLayoutEffect` re-asserts the live transform after every render so a filter
change can never silently discard the user's pan.

Measured over a 40-step drag: **3 long tasks before, 0 after**; gesture wall
time 6.9s to 5.4s (Playwright's own CDP round-trips dominate that figure).
Worth recording: **DOM mutation count was identical (~40) in both versions** and
is therefore useless as a proxy here — React already wrote only the changed
attribute. The cost was the reconciliation pass over 3,528 nodes, which is what
`longtask` sees and `MutationObserver` does not.

## The wait may not cost the reader anything

The loading screen said "Loading taxonomy tree…" under a logo. It now rotates
five questions the tool exists to answer, one every ~4s, each with a
supporting line. Placement leads and known-vs-unexplored closes.

The constraint is the design. `LoadingQuestions` owns no exit animation, no
minimum lifetime and no grace period for the question on screen: the parent
unmounts it the instant the tree is ready, mid-sentence. On a warm API that
means a flash of question one and nothing else, which is correct — padding a
load to fit more copy trades the reader's time for our word count.

It lives in **both** loading states. The splash covers the whole screen during
the first fetch, so questions placed only in `page.tsx` would never be seen
while the tree actually loads; the in-page state is what a later taxonomy
switch shows. One component, two grounds — chrome under the logo, paper in the
stage — and no colour invented for either.

The provenance line beneath is real or absent. It renders only once
`/api/v1/provenance` answers, and is allowed to lose the race to the tree and
never appear; a row of zeros would be a claim about the corpus that nothing had
supported yet. It says "clusters", not "curated clusters", because `bgc_count`
holds MIBiG entries and antiSMASH predictions both — and the fifth question on
that same screen promises to keep those apart.

Three faults only running it caught, none visible to the types or the build:
the group overflowed a 768px-tall laptop and sat ~90px low; the margin that
fixed that ran the first question through the logo under
`prefers-reduced-motion`, where the fallback is a landscape still with no blank
band to reclaim; and the provenance line orphaned a date onto its own row at
34rem. Reduced motion gets question one, held still — a crossfade is motion.

The rotation is `aria-hidden` with a single `sr-only` status carrying "Loading
taxonomy tree…", so a screen reader is told the app is working once rather than
re-read a new sentence every four seconds.

`vitest.config.mts` gained the `@/` alias `tsconfig` already gives the app.
Vitest does not read tsconfig paths, so before this any test importing a
component died on that component's own `@/lib/...` imports.

## An exact identifier match can still be the most confident wrong answer

`ingest/link.py` graded an exact NCBI taxid match as STRONG with no further
test. An identifier had matched an identifier, which looks like the safest join
available. **Only one of those two identifiers is derived from the genome.**
GTDB assigns a lineage from genome content; the NCBI taxid is typed in by
whoever deposited the assembly. When the depositor was wrong, an exact match
put the cluster in the wrong phylum and stamped it with the highest confidence
the schema can express.

Auditing the shipped corpus against `bac120_metadata` found 73 clusters whose
assembly carries two lineages naming different phyla. 41 are GTDB suffix splits
(`Myxococcota` vs `Myxococcota_A`) and are not errors. The other **32 were
real, all STRONG, and all trace to five assemblies** — four MAGs plus one
isolate deposited as *Bacillus subtilis* that is 67.4% GC, where *B. subtilis*
sits near 43.5%.

`Genome.ncbi_taxonomy_conflict` is tri-state, for the reason `is_mag` became
tri-state one migration earlier: True means the two lineages disagree at phylum
rank, False means they were compared and agree, NULL means nobody compared
them. `ingest gtdb` establishes it from GTDB's own adjacent `ncbi_taxonomy`
column, so — unlike the `is_mag` case — this loader has genuine grounds for
what it writes, including None.

An identifier-based placement onto a conflicted assembly is demoted to WEAK
with a caveat naming the reason. The method is still recorded truthfully; what
changed is what the match is worth. **NULL is not demoted** — unknown is not
suspicion, the same rule the coverage model applies to unexamined genomes.

A GTDB suffix split is deliberately not a conflict. The comparison is at phylum
rank only, where disagreement is never nomenclatural drift. Genus and species
disagreements are routine — GTDB reclassifies 27% of MIBiG's organism labels —
and are correctly unflagged.

`bgcscape recheck-placements <bac120_metadata.tsv[.gz]>` backfills the column
and re-grades an existing database; re-running the whole ingest would work and
is far more than the job needs. It is **symmetric**: a placement demoted by a
conflict is restored if a later GTDB release resolves it, because a one-way
ratchet would leave a corrected assembly penalised forever — the mirror of the
original bug.

The migration adds the column as NULL everywhere rather than False. The
comparison needs a column that lives in the metadata TSV and not in this
database, so nothing here can establish the answer and nothing here asserts
one.

`read_gtdb_metadata_tsv` now reads `.tsv.gz` directly — that is how GTDB ships
these files, and `bac120_metadata` is ~2 GB expanded.

## "Same BGC" finally has a sequence meaning

`bgc_family` held 279 `compound_group` rows and **zero** `sequence_family`.
Every "these two clusters are the same" this database could express traced back
to MIBiG recording the same named compound — a curated chemical fact, never a
sequence comparison. `ingest/bigscape.py` and `ingest/bigfam.py` were both
implemented and tested against real output formats; neither had ever been run
against anything.

A BiG-SCAPE 2.0.3 run over MIBiG 4.0 (2,636 GBKs, 2,631 records, Pfam-A,
glocal/region, mix weights, cutoff 0.3) supplies one:

    3,459,765 edges -> 282 connected components
    802 records in 289 families at c0.3
    ingest: created=747, updated=0, skipped=55

The 55 skips are BGC0003xxx entries in MIBiG 4.0 that postdate this corpus's
MIBiG snapshot — the expected-not-an-error case the ingest counts separately.
93% of the clustering joined on `external_ref` with no transformation, exactly
as the module docstring predicted.

**The `AnalysisRun` matters as much as the families.** It records
SEQUENCE_CLUSTERING over the 505 genomes the run actually reached, so "this
cluster is in no family" now means "nothing similar was found" for those
genomes and still means nothing at all for the other 1,037. Without it the
ingest would have made every unclustered cluster in the corpus read as a
similarity claim about a comparison that never happened.

Two downstream paths were dead for want of this data, not for want of code.
`/api/v1/prioritization` could compute none of its five components;
`family_rarity` and `taxonomic_isolation` now resolve over 1,227 clusters on
505 genomes. `api/comparison.py`'s "two clades sharing a SEQUENCE_FAMILY share
gene content" had no sequence family to share. `class_rarity_in_clade` is still
uncomputable and still says so — that needs a recorded *cluster-detection* run,
which is the antiSMASH half of this pair.

The families are not merely non-empty, they are coherent. FAM_00016, the
largest at 27 members, is polyketide-containing throughout — 22 `pks` plus 5
saccharide hybrids (`pks+saccharide`, one of them `other+pks+saccharide`) — and
not a mixed bag. Across the 264 multi-member families, 111 have all members inside
a single curated compound group and 30 span several. **The remaining 123 have
no member in any compound group at all**: sequence-coherent families curation
never named, which is the case for ingesting this that the compound groups
could not make.

The mix bin was ingested, not the class bins. The run also emitted a
`Categoryless` bin holding all 2,631 records and the same 282 components —
MIBiG GenBanks carry no antiSMASH category annotation, so class binning had
nothing to bin on and produced a duplicate. Nothing is lost by taking mix; a
run over antiSMASH output would make that bin real.

Recorded as 2.0.3 against the image's own reported version, not the CLI's
2.0.0 default. The version is on the Source row, the AnalysisRun, and each
family's `clustering_method`, and a family label is meaningful only within one
cutoff — so a wrong version here is a wrong provenance claim on all 281.

## A big number can hide a small one

DEPLOY.md told anyone looking for BiG-FAM's families that the bulk download is
a 189 GB tarball and pointed them back at per-GCF web exports. The number was
real and the conclusion was wrong: it is three components, and two are not GCF
data.

    subpfam_sources     144 GB   HMM training material
    full_input_data      28 GB   the input GenBanks
    full_run_result      17 GB   the families

Walking the paper-data index down to `data/full_run_result/result/data.db` puts
the real cost at 17 GB. Recorded with the three things that decide whether it is
worth paying: it does not plug in (`ingest bigfam` reads BiG-FAM's web export
TSV, and this is a BiG-SLiCE SQLite — but `bgc.orig_folder`/`orig_filename`
carries the assembly+region pair the ingest already splits, so the bridge is a
script, not a second ingest module); the snapshot is July 2020 against GTDB
R11-RS232 from April 2026, so coverage must be measured before the download,
not assumed after it; and whether `membership_value` is on the same scale as the
web export's RADIUS is **unverified**, which is load-bearing because the ingest
thresholds RADIUS at 900.

## The policies were written for the wrong kind of site

The first production-readiness pass wrote the policy pages for a commercial
website, because that is what the audit checklist described. This is not one.
Company registration numbers, VAT numbers, consumer-law liability clauses and a
choice-of-forum clause are all wrong on a research tool heading for a journal —
they invite a reader to believe a legal entity stands behind this that does
not, and they were nineteen fields of friction in front of a submission.

Terms & Conditions became Terms of Use and lost the commercial half entirely.
What replaces it is what an academic tool actually needs to say: use it freely,
build on it, cite it. The disclaimer stays, because "as is, no warranty" is
what the MIT licence the code already ships under says, now applied to the
hosted instance too. So does the section on what the output claims — the
prioritisation score is an ordinal ranking aid and not a novelty claim, absence
is evidence only where a run was recorded — because misreading that is how this
tool could contribute to a wrong result, which is a scientific risk rather than
a legal one.

**Every unresolved fact lives in one file.** `web/src/lib/project-info.ts`
holds affiliation, contact, DOI and citation; a value left as `TODO()` renders
in the page body as a visible oxblood marker rather than as blank space or an
invented fact. Filling that file completes the policy pages, the citation block
and the availability statement together, so nothing can be updated in one place
and missed in another. Nineteen scattered placeholders became seven distinct
facts.

Ten tests cover the placeholder mechanism itself, including the two failures
that would be worst to ship: a `TODO` stringifying to `[object Object]` in the
middle of a policy page, and an empty string being mistaken for one. Both look
like finished copy at a glance.

Citation is first-class because it is what actually protects this work.
`CITATION.cff` gives GitHub its "Cite this repository" button and gives Zenodo
something to read when minting a DOI; the site carries the same citation in
copyable form, and the rail footer links it as "Cite this tool" rather than
"Data sources" — the verb gets clicked by people who skip a label that sounds
like documentation. GTDB's CC BY-SA 4.0 is called out three times — policy
page, README, CITATION.cff — because it is the one licence in the chain that
constrains what the *author* may do, not just what a user may do.

## A front door that states its terms

The explorer shipped as a single route with no policy pages, no favicon, no
share card, no sitemap, no 404, and no `h1`.

The privacy story is genuinely clean and it is worth recording *why* rather
than only *that*: no cookies, no localStorage, no analytics, no tag manager, no
pixel, no embeds, and fonts self-hosted rather than pulled from a CDN — checked
by grep across `src/` and `e2e/`, not assumed. So the Cookie Policy says there
are none and explains that this is why no consent banner appears; a banner on a
site that sets nothing would train readers to dismiss the ones that matter.

**The upload form collected personal data with no notice.** It takes files and
an organism name and writes them into the SHARED corpus every other visitor
browses, served back out through a public API — a publication, not a private
analysis, and the form never said so. It now leads with that and requires an
unticked consent box. Unticked because consent has to be an act.

**The same form could not be used without a mouse.** The drop zone was a `<div
onClick>` wrapping a `display:none` file input — a div has no role, no tab stop
and no keyboard activation, and a `display:none` input is not focusable, so
between them there was no way to choose a file from the keyboard at all. It is
a real `<button>` now, with the input moved out and kept `sr-only`. Focus moves
in on open and back out on close, Tab is trapped, the organism field carries
`aria-required`/`invalid`/`describedby`, and errors are announced through
`role="alert"`. The submit button is no longer disabled when the form is
incomplete — a disabled control announces nothing and gives a reader no way to
learn why it will not respond.

`ink-faint` carried **2.56:1** on paper against WCAG AA's 4.5:1, and the token
is used as *text* in 42 places, most at 10–11px where the large-text allowance
does not apply. Darkened along the same hue to `#6C6E68`: 4.81:1 on paper,
5.16:1 on card. Changed in `colors.ts` too, because the SVG canvas draws the
"+N more" counts, the empty-state line and the donut's centre label in that
copy. The hierarchy is flatter; the alternative was a tier some readers cannot
see.

The document had no `h1`. The wordmark is an `<img>` and the only headings were
the `<h2>`s inside two dialogs, so the outline started at level 2 and a screen
reader landing on the page was told nothing about what it is. Added `sr-only`;
the canvas region became `<main id="main">`, which is the skip link's target.
Global `:focus-visible` rings, because several controls set `outline-none` and
replaced it with a border-colour change; on the near-black chrome the oxblood
ring is invisible at 1.79:1, so the lifted accent is substituted there.

The favicon is **drawn, not cropped**. The wordmark is a 710x218 landscape
lockup and reducing it to 16px produced mud. Each `.ico` tier is drawn at its
own size with detail as a function of size — two tips and no ticks at 16, three
at 32, four at 48/64 — so nothing is a downscale of a denser drawing. Frames
are RGBA because Next's ICO decoder rejects RGB ones, which is a build error
rather than a bad render.

`NEXT_PUBLIC_SITE_URL` is new and load-bearing. Without it `metadataBase` falls
back to localhost, which makes `og:image` relative — dropped by most crawlers,
so the share card silently vanishes — and puts localhost in `sitemap.xml`.

## A quarter of the logo was unused alpha

`logo.png` was a 148 KB RGBA file whose alpha channel is fully opaque at every
pixel, fetched on every page load and displayed at a height of 22–26px.
Dropped to RGB and quantised to 256 colours: 93,537 bytes, **37% smaller**; the
Open Graph card went 147 KB to 96 KB.

Quantisation was measured before it was applied. RMSE against the original is
1.27 on a 0–255 scale, compared at 2x on the crop that could actually band —
the gene arrows, the only gradients in the mark — alongside the letterform
anti-aliasing. 64 and 128 colours were cheaper (75 KB / 84 KB) and were **not**
taken: they cross into RMSE 4.07 and 2.55 on artwork whose whole job is to be
the brand.

## The renderer was never the hole

The write half of this API is unauthenticated by design and had no ceiling on
anything: no rate limit, no request-body cap, no security headers, and a
container running as root.

The correction is the interesting part. `/api/v1/export` renders caller-supplied
SVG through cairosvg, which reads as an SSRF and local-file-read vector.
Reading cairosvg's own source rather than trusting the shape of the API: with
the default `unsafe=False` it parses through defusedxml with `forbid_entities`
and `forbid_external` set, and substitutes `url.safe_fetch`, which resolves only
`data:` URLs and returns a blank 1x1 SVG for everything else. No SSRF, no file
read, no XXE.

**The hole was one layer earlier, in our own code.** `embed_view_config`,
`add_provenance_caption` and `extract_view_config` each parsed the untrusted SVG
with stdlib `xml.etree` *before* cairosvg saw it, and stdlib honours internal
entity declarations. Measured, not asserted: a 359-byte billion-laughs document
expands to 1,000,000 characters in 0.02s, and each further nesting level
multiplies by ten. All three now share one `_parse_svg` that goes through
defusedxml and checks size before building a tree, parametrised over all three
entry points — because a fix applied to one would have left the other two open,
which is how this class of bug comes back.

`defusedxml` is a **core** dependency, not part of the `export` extra.
`inspect-figure` and the metadata embed read SVG on deployments that have no
Cairo and never install that extra. Depending on another package's transitive
dependency for a security control is how the control quietly disappears.

Rate limiting states its limits and its honest scope: 20 requests per 5 minutes
per client over `/api/v1/ingest` and `/api/v1/export`; reads are untouched
because the tree *is* the product. It is an in-process counter — it resets on
restart and two containers each get their own allowance. That is honest for one
free-tier container and it is not a defence against a distributed flood, which
belongs upstream. Saying so in the module docstring matters more than the code
does. **It is kept on in tests**: the suite exposed the trade immediately — four
upload tests failed in the full run and passed alone, because the twenty-first
request in a shared process is a 429 regardless of which test makes it. An
autouse fixture clears the counters between tests instead of disabling the
middleware, so what ships is what is exercised.

CORS is documented as *not* being the control it looks like. Every route is
unauthenticated and cookieless, so an origin allow-list governs what other pages
may READ in a browser and stops nothing else; a curl reaches the upload endpoint
either way. The things that actually bound abuse are the rate limit, the size
caps and `BGCSCAPE_ALLOW_UPLOADS=0`.

**The frontend CSP was written strict, tested, and loosened on evidence.**
`script-src 'self'` built fine and broke the app: every route threw React error
#412 with two violations per page, because Next's App Router ships hydration
state in inline scripts. The supported fix is a per-request nonce, which Next's
own docs say requires dynamic rendering — trading static delivery of all eleven
routes for a server invocation per request. Against an app that renders no
user-supplied HTML anywhere (no `dangerouslySetInnerHTML`, no `innerHTML`
outside a test, no `eval`, no d3 `.html()`), `'unsafe-inline'` is the better
trade, and the reasoning is in the config so the next reader sees a decision
rather than a default. The directives still doing work are `object-src 'none'`,
`base-uri 'self'`, `form-action 'self'` and a `connect-src` naming exactly one
API origin.

The container drops to an unprivileged user (uid 10001). It parses anonymous
uploads, so the blast radius of a parser bug should not include root. `/app/data`
is chowned as a **directory**, not just the file — SQLite creates `-wal` and
`-journal` siblings, and chowning the database alone fails at the first write
with a misleading "readonly database".

Server-side validation on the two free-text fields: the browser capped organism
at 200 characters, which protects nothing when the endpoint is reachable without
the form, and both fields are rendered back to every visitor.

## Authorship is a claim, and the file says which kind

`project-info.ts` and `CITATION.cff` agree on the authors, affiliation, contact
and wordmark provenance, which is the point of having put them in one place.

Two authors, both with ORCIDs, and both ORCIDs **verified rather than pasted** —
the identifier carries an ISO 7064 MOD 11-2 check digit, so a transposed pair is
catchable before it reaches a manuscript. The second author's affiliation is
recorded as INFERRED from the division named for the first author, at the line
where it matters: it is the kind of detail that is obviously right or obviously
wrong to the person concerned and invisible to everyone else, so it is better
recorded as an assumption than as a fact. The correspondence address is the
institutional one — it is what verifies the affiliation to a reader, and a
commercial address has no place on an academic tool.

The wordmark is recorded as "created for this project by Kartik Juyal using
Google Gemini", which is what is true and is the form that survives being
questioned. Naming the generating tool is not a hedge: a growing number of
journals require AI-assisted artwork to be disclosed at submission, and the
tool's own terms are what govern the output.

Four facts remain unresolved and all four are deferred by construction, not
overlooked: the Zenodo DOI cannot exist until a release is archived, the paper
citation until one is published, and the hosting regions and platform-cookie
check until there is a live domain to check them on.
